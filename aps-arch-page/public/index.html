设计总纲

本方案在 PRD 第 2 章架构基础上做可直接指导开发的细化，贯穿三条原则：解耦（业务层不感知具体求解器）、可扩展（引擎/Agent/行业模板可插拔）、开源友好（Apache-2.0、模块边界清晰、无隐性商业依赖）。所有设计严格限定在 MVP（v0.1）范围：以 Timefold 单引擎 + 基础约束 DSL 为核心，Agent 能力仅做接口与数据预留，不提前实现。

MVP 架构定位（务实、不过度设计） MVP 交付的实质是「开箱即用、中文原生、带约束 DSL 与 Justification 的 Timefold APS」。双引擎中的 Agent 引擎（异常重排 / NL→DSL / what-if / mfg-agent 对接）按 PRD 明确推迟到 v0.5，MVP 仅保留 SolverAdapter 抽象、事件总线消息契约、ConstraintJustification 持久化三个「扩展锚点」，为 v0.5 铺路而不实现。

1.1 算法引擎层与业务层的解耦设计（重点）

业务层通过统一 SolverAdapter 接口调用求解，同步用于 ATP 快速预估、异步用于主排产。接口与 DTO 全部落在 solver-api，保持引擎中立（不含任何 Timefold 注解/类型）。

SolverAdapter 统一接口方法定义

public interface SolverAdapter {

    EngineType engineType();                       // TIMEFOLD / ORTOOLS / RULE_BASED

    // 同步求解：用于 ATP FAST 预估（<1~2s），阻塞返回
    ScheduleSolution solve(ScheduleProblem problem, SolveConfig config);

    // 异步求解：用于主排产。返回句柄，任务状态入 DB+Redis，进度经 WebSocket 推送
    SolveHandle submitAsync(ScheduleProblem problem, SolveConfig config);

    // 提前终止（对应 Timefold SolverJob.terminateEarly()）
    boolean terminateEarly(String solveTaskId);

    // 进度查询：当前得分 / 收敛曲线（Timefold 2.8 SolverJob 不提供步数计数）
    SolveProgress getProgress(String solveTaskId);

    // 增量重排：以上次解为起点，仅重排未冻结任务
    ScheduleSolution solveIncremental(ScheduleProblem problem,
                                      ScheduleSolution startingSolution,
                                      SolveConfig config);
}

入参 / 出参数据结构（引擎中立 DTO）

结构关键字段说明
ScheduleProblem（入参）orders、resources、routings、calendars、setupMatrix、strategy、frozenAssignments、sandboxId由「问题装配器」从 DB 组装；对应 Timefold 的 @PlanningSolution，但注解只在 solver-timefold 内的包装类上
TaskAssignmenttaskId、orderId、operationIndex、resourceId、secondaryResourceIds、startTime、endTime、setupStart/End、sequenceInResource、pinned(冻结)Timefold 的 @PlanningEntity；资源以 List Variable 持有任务序列
SolveConfigterminationSeconds(默认60)、moveThreadCount、acceptorType(默认 LATE_ACCEPTANCE)、mode(FAST/ACCURATE)、idempotencyKey求解配置，运行时可调；Timefold 2.8.0 社区版不支持多线程求解，moveThreadCount 仅企业版可用，MVP 不启用
ScheduleSolution（出参）scoreHard、scoreSoft、assignments[]、justifications[]、metrics、status(SOLVED/TIMEOUT/INFEASIBLE)回写 task 表 + constraint_justification 表
SolveMetricselapsedMs、收敛曲线采样、bestScoreHistory前端进度与性能分析；不再输出 stepCount / unimprovedStepCount（Timefold 2.8 的 SolverJob 无该计数，恒 0 属失真）
ConstraintJustification(DTO)constraintId、constraintName、scoreImpact、implicatedFacts(taskId/resourceId/orderId)MVP 必须持久化，为 v0.5 中文归因（FR-AG-003）预留数据

同步 / 异步调用方式

  • 异步（主排产）：submitAsync 基于 Timefold SolverManager 提交 SolverJob，任务状态机 PENDING→RUNNING→SOLVED/FAILED/CANCELLED/TIMEOUT 落 PostgreSQL，进度写 Redis，经 WebSocket 推前端。同一 Sandbox 同时仅一个 RUNNING（可配置排队/拒绝）。服务重启后以 DB 为准恢复或标记失败。
  • 同步（ATP FAST）：MVP 属 Should Have；接口保留 solve() 走构造启发式（First Fit），P95<2s，不落主计划仅在 Sandbox 计算。

1.2 Agent 层与业务层的交互协议（MVP 预留，v0.5 落地）

MVP 不实现 Agent 业务能力，但需固化三类「契约锚点」，避免 v0.5 返工：

  1. 事件总线消息格式（Redis Stream，MVP 仅用于订单状态/求解完成事件；异常事件通道预留）： 
    {
  "eventId": "EVT-20261103-001",
  "eventType": "SCHEDULE_SOLVED | ORDER_CONFIRMED | EQUIPMENT_FAILURE(预留)",
  "source": "APS | MES | mfg-agent | MANUAL | SYSTEM",
  "tenantId": "...",
  "timestamp": "2026-11-03T10:00:00Z",
  "traceId": "...",
  "payload": { /* 事件详情，如 solveTaskId / resourceId / affectedTasks */ }
}
  2. Tool 接口定义（MVP 定义 Schema，不实现调用）：aps.schedule(orders, strategy)、aps.atp(product, qty)、aps.explain(taskId)、aps.whatIf(scenario)。Tool 内部一律回调 aps-service 的公开接口，不直连 DB / solver。
  3. 与 mfg-agent-platform 对接规范：APS 暴露 /api/v1/integration/agent/* 系列端点，采用标准 REST + Webhook，不强依赖特定 Agent 框架；MCP/A2A 注册与 gRPC 直连为 v0.5 事项。降级要求：对方平台不可用时 APS 独立运行不受影响。
解耦红线 Agent 只能通过 Tool → service 接口访问能力；Agent 生成的约束 DSL 必须经沙箱验证 + 人工审核才能进入生产求解（PRD BR-SE-005-05 / BR-AG-002-04）。MVP 阶段该链路仅保留数据与接口占位。

2. 技术栈落地方案

2.1 后端

  • 框架版本：Spring Boot 3.3.x + Java 21 LTS + Maven（Timefold 1.35+ 要求 JDK 21）。
  • 持久层选型：MyBatis-Plus（推荐）。理由：① 甘特图/齐套/审计等复杂报表与多表关联查询需要精细 SQL 控制；② PostgreSQL JSONB 扩展属性（ext_attrs / industry_attrs）用自定义 TypeHandler 处理更自然；③ 契合阿里 Java 规范与国内团队心智；④ 求解领域对象是独立 POJO（非 ORM 实体），用装配器在 DB 模型与 ScheduleProblem 间转换，避免 JPA 懒加载与求解器对象图冲突。JPA 更适合纯 CRUD，本项目查询形态偏复杂，故选 MyBatis-Plus。
  • 异常处理：全局 @RestControllerAdvice；业务异常 BizException(errorCode, args)；校验异常统一转字段级错误；HTTP 语义码对齐 PRD（409 冲突 / 422 业务不可处理 / 400 参数 / 403 权限 / 429 限流）。
  • 统一返回封装： 
    { "code": 0, "message": "success", "data": {...}, "traceId": "xxx" }
    错误码：0 成功、4xxxx 客户端、5xxxx 服务端；写操作支持 Idempotency-Key；分页 page/size/sort（size 默认 20、最大 200）；默认限流 100 req/min/user。

2.2 前端

  • 技术栈：Vue 3.4+ + TypeScript + Vite + Element Plus + Pinia + Vue Router + Axios（统一拦截 Result/错误码/traceId）。
  • 甘特图 MVP 最终选型（对齐 PRD 2.2）：MVP 采用开源 vue-ganttastic 承载资源/订单甘特图基础渲染，拖拽与实时可行性校验用自研交互层补齐（同/跨资源拖拽、工序依赖/日历/换型前端预校验、冲突高亮、负载热力）。不引入商业 Bryntum（GA 再评估）。
    兜底策略M1 必须完成甘特图 PoC（任务 M1-FE-06，关键路径）。若 vue-ganttastic 在大数据量（5000 任务）虚拟滚动或拖拽性能不达标，则切换到基于 ECharts custom series 自研甘特图层，接口契约不变。前端只暴露统一的 GanttAdapter，隔离底层库。
  • 工艺路线 DAG 编辑器与甘特图共享图形交互基建；大数据量场景统一采用虚拟滚动 + 分页加载。

2.3 中间件

  • PostgreSQL 15+：见第 4 节表设计规范。启用 pgcrypto（gen_random_uuid）、pg_trgm（名称模糊查询）。
  • Redis 7 使用场景清单：① 分布式锁（Redisson，求解任务/发布互斥）；② 求解进度缓存与收敛曲线；③ 幂等键（Idempotency-Key）短期存储；④ JWT 刷新/黑名单；⑤ 系统配置缓存（发布订阅热更新）；⑥ Redis Stream 作为 MVP 事件总线。
  • 消息队列选型确认：MVP 用 Redis Stream（契合「轻量部署 ≤4C8G、单机 Docker Compose」目标，避免多一个 RabbitMQ 容器与运维）。RabbitMQ / Kafka 推迟到 GA（多副本、跨系统高吞吐场景）。
  • MinIO：附件（图纸、贴片程序、钢网照片），MVP 端口内部化不对外暴露。

2.4 Timefold Solver 集成方式（重点）

维度内嵌式（同 JVM，MVP 推荐）独立求解微服务（GA 演进）
集成方式timefold-solver-spring-boot-starter，SolverManager 本地提交独立进程/容器，gRPC/REST 调用
优点零网络序列化开销、部署最简、契合 4C8G 单机求解与业务隔离、可独立水平扩展、OOM 不影响主服务
缺点求解吃 CPU/内存与业务同进程；大规模分区受限需序列化 Problem/Solution、运维复杂度上升
适用MVP：≤500 工单/50 资源，单引擎GA：≥500 工单分区搜索、CP-SAT 并存、多副本

推荐路线：MVP 内嵌式（aps-admin 同 JVM 加载 solver-timefold）。因已用 SolverAdapter 抽象隔离，GA 阶段将 solver-timefold 抽为独立服务时，业务层零改动，仅替换 Adapter 实现为远程调用即可。OOM 风险 MVP 内通过「降级分批求解（按产品线拆分）+ 单线程限时求解」规避；社区版无多线程，不使用 moveThreadCount。

10solve_task求解任务生命周期idempotency_key 幂等；状态机

配套表（次核心，MVP 亦需）：constraint_justification（归因数据预留）、sandbox（场景）、audit_log（审计）、users/role/permission（RBAC）、task_adjustment（调整历史/撤销栈）。

4.2 主键、软删除、JSONB 规范

  • 主键策略：业务主数据用 UUID（gen_random_uuid()，租户安全、分布式友好）；高频大表（task / audit_log / solve_task）用 BIGSERIAL 或雪花 ID（索引更紧凑、写入更友好）。对外一律另设业务编码（code / order_no）供人类可读与唯一校验。
  • 软删除规范：统一 deleted BOOLEAN DEFAULT false；所有查询经 MyBatis-Plus 逻辑删除拦截自动过滤；唯一约束带 WHERE deleted=false 部分索引；删除前做引用校验（PRD BR-MD-001-07 等），被引用则拒绝或转软删除并标记。
  • 通用字段：tenant_id（MVP 单租户默认值，字段与过滤拦截器预留）、version（乐观锁）、created_at/updated_at/created_by/updated_by。
  • JSONB 使用规范：仅存放扩展属性（ext_attrs）与行业属性（industry_attrs）及快照/明细（bom.items、routing.nodes/edges、strategy.rules、payload、snapshot）。凡参与排产计算或高频过滤的字段必须结构化成列（如 capacity_mode、due_date、priority、start_time），不得塞进 JSONB。JSONB 建 GIN 索引；约定每个 JSONB 字段的内部 schema 并在开发者文档固化，避免"无 schema 膨胀"。

4.3 关键索引与查询性能要点（对齐 PRD 8.3）

  • task(sandbox_id, resource_id, start_time) —— 资源甘特图时间轴查询（覆盖索引，避免回表）。
  • task(order_id, operation_index) —— 订单工序链查询。
  • orders(tenant_id, status, due_date) —— 订单池按状态+交期检索。
  • solve_task(sandbox_id, status, created_at) —— 求解任务列表与并发控制。
  • audit_log(tenant_id, created_at DESC, action) —— 审计按时间倒序分页。
  • JSONB GIN：ext_attrs / industry_attrs / payload。
  • 性能要点：甘特图按时间范围 + 资源分页查询而非全表；单表控制在千万行内、超量走分区（按时间/租户，PRD 三期）；报表类查询用只读副本（GA 读写分离）；BOM 多级展开用递归 CTE 并限深（≤20 级）+ 环检测。

6. 架构风险与应对（Top 5）

R1 · Timefold 求解性能不达标（500 工单 <60s） 影响：核心 SLA 失守。MVP 规避：① 构造启发式用 First Fit/GoodFirstFit 提供高质量初始解；② 社区版单线程求解，不依赖 moveThreadCount，改用「限时 + bestScoreImproved 稳定」双条件 termination；③ 大规模走分区/分层求解（按产品线/车间拆分）；④ 增量重排复用 startingSolution；⑤ M2 起即用种子客户真实数据压测（任务 M2-QA-01），而非上线前才验证。已实测：≤50 单 / 300 任务可解，200/300/500 单超时（见「执行进展」）。
R2 · 甘特图交互与大数据量渲染 影响：拖拽卡顿、5000 任务渲染超 3s。MVP 规避：① M1 前置 PoC（M1-FE-06，关键路径），尽早暴露 vue-ganttastic 能力边界；② 统一 GanttAdapter 抽象，保留 ECharts 自研兜底；③ 虚拟滚动 + 按时间/资源分页；④ 拖拽前端本地预校验（工序依赖/日历/换型）+ 后端二次校验，减少无效请求。
R3 · 约束 DSL 代码生成安全（JavaPoet 热加载字节码） 影响：恶意/错误代码注入、热加载导致求解崩溃。MVP 规避：① MVP 收敛 DSL 能力——仅支持「8 种内置规则的参数化 + 权重 + 条件过滤」，不开放任意 Constraint Stream 自由编写；② 生成代码走白名单 API + 沙箱校验（语法/类型/字段引用编译期拦截）；③ 热加载失败自动回滚上一版本；④ Agent 生成 DSL 强制人工审核（v0.5 才接入 LLM 生成）。
R4 · 双引擎抽象不当导致返工 / 过度设计 影响：为未落地的 CP-SAT 过度设计，拖慢 MVP。MVP 规避：① SolverAdapter 以 Timefold 真实需求为准设计，但 DTO 保持引擎中立；② solver-ortools 仅留空壳接口 + 配置开关，不实现（对齐 PRD Won't Have）；③ 引擎路由 MVP 仅 Timefold 单路由 + 规则引擎兜底，CP-SAT 路由规则预留不启用。
R5 · 行业特性（SMT 拼板/换型、储能分选）与数据模型耦合、JSONB 膨胀 影响：模型僵化、查询劣化、行业扩展困难。MVP 规避：① 行业专属字段进 industry_attrs JSONB，核心排产字段结构化建列；② 行业能力以模板 + 配置扩展（工序模版/换型矩阵/约束规则），不改核心代码；③ 换型矩阵 MVP 可先用默认值（Should Have），完整实现放 v0.5（V05-08）；④ 每个 JSONB 字段固化内部 schema 并加 GIN 索引。

7. 给项目负责人的 3 条架构落地核心建议

建议一 · 守住「单引擎 MVP」的边界，把双引擎做成锚点而非负担 MVP 的最大风险不是技术，而是范围蔓延——被"双引擎/Agent"卖点诱导提前实现 LLM 能力。应严格锁定 MVP = Timefold 单引擎 + 基础 DSL + 甘特图闭环，仅用 SolverAdapter 抽象、事件总线消息契约、ConstraintJustification 持久化三个低成本锚点为 v0.5 铺路。凡是 PRD 标注 Won't Have 的（CP-SAT / NL→DSL / 异常感知 / mfg-agent 对接），MVP 一律不做。
建议二 · 把两个"高危前置项"放到 M1 就做技术验证，别拖到联调 甘特图选型（M1-FE-06）与 Timefold 建模+性能（M1-SE-02/03、M2-QA-01）是全项目成败关键路径。要求 M1 内完成甘特图 PoC 与 Timefold 最小闭环求解，并尽早引入种子客户真实数据做规模压测。性能与交互问题越晚发现，返工成本越高——这两项一旦在 M1 验证通过，M2/M3 就是确定性工程。
建议三 · 用「模块依赖红线 + API 契约先行」保障多人并行不互相阻塞 第 0 周必须冻结 API 契约（P0-08）与模块依赖方向（P0-01），并写入 CI 门禁（Checkstyle/ArchUnit 校验分层依赖、禁止 solver 实现类型泄漏到 service/web）。四个角色组（基础数据/排产引擎/前端/测试部署）据此并行开发，前端用 Mock 与契约解耦后端进度。开源友好性也由此保证：清晰边界 + 契约文档 = 社区贡献者低门槛上手。

第二部分 · 分阶段协同开发任务节点拆解

以 MVP（v0.1，3 个月）为核心，按四个角色组（后端基础数据组 / 后端排产引擎组 / 前端组 / 测试部署组，另含架构/全体）拆解，支持多人并行。下方交互式任务看板可按里程碑/角色筛选、高亮关键路径，并可更新任务状态与负责人（持久化到数据库）。
