# 30 分钟现场演示脚本：主计划插单重排

> 适用版本：2026-11-05 起（`aps_demo` 种子库 / 后端 dev / 前端 Vue 3）。
> **日期口径**：种子数据全部相对 `-AnchorDate` 生成，**现场一律说“演示当天 +N 天”**，不要念会过期的绝对日期。
> 演示对象：制造业计划部、生产部、信息化负责人。
> 演示目标：让客户看懂“订单进来以后，计划员怎么在系统里判断、调整、留痕”，而不是逐个点菜单。

## 〇、演示坐标速查（`aps_demo` 种子库）

| 坐标 | 值 | 预期 |
|---|---|---|
| 六单可排集合 | `DM-SO-1002` ~ `DM-SO-1007` | 求解 `SOLVED / hard=0 / soft=0 / unassigned=0`；场景共 **48 道工序**，本次只重排窗口内工序（今天 48 道 / 保留 0；11-09 演示日 47 道 / 保留 1） |
| 缺料演示单 | `DM-SO-1010`（DRAFT，无工艺路线，不排产） | 单张 MRP `SHORTAGE`，缺 `RAW-BMS-001` 40 套；单张求解 `422/42200` |
| 齐套对照单 | `DM-SO-1008`（90 台） | 单张 MRP `FULL`（已齐套，不再承担缺料镜头） |
| 七单合计 | `DM-SO-1002` ~ `DM-SO-1008` | `422/42200`，`缺料物料: RAW-ELEC-002`（缺 154 只） |
| 冻结坐标 | 1003 / 1004 / 1005 | 1003 任务级 `FROZEN`（8 条）；1004 op4 `RESOURCE` 锁 `RES-MODULE-01`；1005 op1 `TIME_WINDOW` |
| 1005 锁窗 | `演示当天 +1 天 08:00–11:00` | op1 落在窗内；重排后仍保持 |
| 1002 锚点 | `演示当天 +6 天 08:00` | 基线自重叠 0 对，重排不撞已有在制任务 |

> 演示口径：**六单看“一键全绿”**（SOLVED / 0 hard / 0 soft；场景共 48 道工序，**本次重排 N 道、保留 M 道**）；**单张 1010 看“缺料拦截”**（SHORTAGE + 422 点名 `RAW-BMS-001`）。两条桥段互不占用同一张订单。

## 一、主线故事（一句话）

六张已确认订单（`DM-SO-1002` ~ `1007`）要在**演示当天**起排进产线；计划员先守住 1003 的冻结机时、1004 的指定模组线与 1005 的客户锁窗（演示次日 08:00–11:00），再把客户新送来的 1010 户用储能样机拿去做缺料判断——BMS 主控缺 40 套，系统直接 422 拦下；随后对六单重排（场景共 48 道工序，只重排时间窗口内的工序，窗口外已完工的保留原记录、不参与重排），得到 0 硬违反、0 软扣分，最后用甘特核对 1005 锁窗与 1002 锚点（演示当天 +6 天），用沙箱与版本做对比留痕。

主线只围绕 **“六单排产 + 一张缺料单”** 两条桥段展开，其他页面都作为“判断依据”出现，不做功能罗列。

   - `FG-ESS-003 V1.0 ACTIVE` 只有 1 行：`RAW-BMS-001`，**只服务缺料演示单 1010，与六单 BOM 完全隔离**。
3. **资源管理** `/master-data/resources`
   - 全量 12 个资源、5 个资源组，全部绑定日历。
   - 关键产能：`RES-PACK-01/02`（PACK 总装线）= 4 台/小时；`RES-AGING-01`（老化房）= 20 工位/7200 秒；`RES-EOL-01`（EOL 终检线）= 20 台/小时。

**台词（可照读）**
> “排产依据的是这条数据链。成品有 001/002/003 三个型号，BOM 展开到半成品和原料；机台这边有 SMT、模组、PACK、老化、EOL 和包装，都挂在班次日历上。工艺路线是 8 道工序的 DAG，哪道工序用哪台机、换型多久，都在这里。排产算的就是这条链上的时间和产能。”

**卡住了怎么救场**
- BOM 结构弹窗加载失败：退回列表，点“明细”看父子件，口头补三层结构。
- 工艺编辑器报错：不进入编辑器，停在列表，用“节点/边”列说明。
- 如果演示库被清过、`FG-ESS-*` 不存在：不要在客户面前造一整套主数据，直接跳到第 4 段，用现有订单讲；缺口按检查清单记录会后补。

**前置数据与缺失时怎么造**
- 需要：14 个物料、6 个 BOM（5 ACTIVE + 1 DRAFT）、12 个资源、4 个日历、3 条 ACTIVE 路线。
- 缺物料/BOM/资源/日历：分别在 `/master-data/materials|boms|resources|calendars` 用“新建”补。
- 缺工艺路线：`/process/routings` 新建，或从导入中心 `routings` 模板导入。

## 第 4 段：订单、冻结与锁定窗口（5 分钟）

**讲什么**：六张可排单怎么进池；在产/客户指定订单怎么用“冻结 / 资源锁 / 时间窗锁”保住已排机时。

**点哪里**
1. `/orders`，全量 10 行（`DM-SO-1001` ~ `1010`），交期在 **演示当天 +20 ~ +53 天**，数量 18~90；10/10 已绑定客户。
2. 讲冻结语义：
   - `DM-SO-1003`：订单级 `FROZEN`，任务级 8 条 `FROZEN`；重排时机时不动。
   - `DM-SO-1004`：订单级 `LOCKED_RESOURCE`，op4 指定 `RES-MODULE-01`。
   - `DM-SO-1005`：订单级 `LOCKED_TIME_WINDOW`，op1 锁定 **演示次日 08:00–11:00**。
3. 讲锚点：`DM-SO-1002` 在 BASELINE 的锚点是 **演示当天 +6 天 08:00**，用于证明重排不会撞上其他订单的在制任务。
4. 点 `DM-SO-1010`：状态 `DRAFT`、无工艺路线，备注“BMS 主控缺料，待评审”；明确它**不进入六单可排集合**。
5. 点 `DM-SO-1008`：90 台大批量单，单张 MRP 已齐套（`FULL`），不是缺料单。

**台词（可照读）**
> “这是本周的 10 张单。能排的是 1002 到 1007 这六张。1003 客户已经锁了交期，它的 8 条任务都是冻结的；1004 指定了模组线；1005 锁的是明天早上 8 点到 11 点这个窗口。冻结和锁定不是把业务锁死，是告诉排产：这些机时别动。1008 是 90 台的大单，料已经齐了；1010 是客户刚送来的样机，BMS 主控没料，先拿它做缺料判断。”

**期望看到**
- 订单列表 10 行，`withCustomer=10`、`distinctCustomers=5`。
- 1003 / 1004 / 1005 的冻结状态分别为 `FROZEN` / `LOCKED_RESOURCE` / `LOCKED_TIME_WINDOW`。
- 1010 为 `DRAFT`，没有工艺路线。

**卡住了怎么救场**
- 冻结报 40901：行版本过期，刷新后重试；仍失败就换 `DM-SO-1002` 讲订单级冻结。
- 客户问“为什么 1010 不能排”：如实说它是 DRAFT、无工艺路线，且 BMS 主控缺料，系统会在 MRP 阶段拦下。
- 确认按钮报 40901：刷新列表再点；不要连续点。

**前置数据与缺失时怎么造**
- 10 张 `DM-SO-*` 订单；1003/1004/1005 的冻结字段与 `ext_attrs.freezeLock`；1002 的 BASELINE 锚点。
- 缺订单：`/orders` → “新建订单”逐张补；也可用导入中心 `orders` 模板批量导入。

## 第 6 段：求解（3.5 分钟）

**讲什么**：把六张可排订单交给求解器重排，观察任务进度和结果；同时用七单演示缺料 422。

**点哪里**
1. `/solve-tasks`
2. “任务号”填 `DEMO-RUN-01`（若提示重复，改 `DEMO-RUN-02`）。
3. “求解引擎”选 `timefold`。
4. “订单号”粘贴六单：`DM-SO-1002` ~ `DM-SO-1007`。
5. 点“提交求解”。
6. 观察状态：`PENDING → RUNNING → SOLVED`；进度条和阶段说明通过 SSE 推送。
7. 成功后记下求解任务 id 与“结果任务”。

**期望看到**
- `SOLVED`、`scoreHard=0`、`scoreSoft=0`、`unassignedTaskCount=0`。
- 返回的 `tasks` 是**本次重排**的工序数，不是场景总数：场景共 48 道工序；今天重排 48 / 保留 0，11-09 演示日重排 47 / 保留 1（1003 工序1 已完工，保留原记录）。
- 冻结语义保留：1003 八条 `FROZEN`、1004 op4 资源锁、1005 op1 时间窗锁。
- 若再提交七单（含 `DM-SO-1008`），返回 `422/42200`：`MRP 齐套未通过（PARTIAL），缺料物料: RAW-ELEC-002`。

**台词（可照读）**
> “现在把六张可排单交给 Timefold 重排。这个场景一共 48 道工序，系统只重排时间窗口内的工序，窗口外已经完工的工序保留原记录、不参与重排——今天这次是重排 48 道、保留 0 道。1003 的冻结任务、1004 的指定模组线、1005 的明天早上锁窗都会保留。求解是异步任务，页面能看到阶段和进度。跑完 0 硬违反、0 软扣分，说明这版计划既可行、也没有明显牺牲交期。再把这七张一起提交，系统会在排产前就用缺料 422 拦下来——缺的是熔断器，不是算不出来。”

**卡住了怎么救场**

**前置数据**

- 七单负例依赖 `RAW-ELEC-002` 合计缺口 154。

### 求解耗时与失败成本（现场口径）

- **单次必然跑满设定预算，不会早停**：求解器要跑满 `timeoutSeconds` 才返回，不要用“十几秒就出结果”做承诺。
- **失败成本**：第一次失败，客户约 **90 秒**看到失败；若服务端再自动重试一次，第二次结果要约 **211 秒**才出来（`2×timeout + 30s` 重试间隔）。第一次失败就点“取消求解”，直接切到上一版甘特讲，不要等第二次。

- **重排/保留的实测口径**（按演示日距基准的天数 k）：`k=0 → 48/0`；`k=1`（11-09 演示日）`→ 47/1`（1003 工序1 已完工保留）；`k≥7 → 40/8`。台词一律说“**48 道工序，其中 N 道本次重排**”，不说“48 任务全部重排”。

## 四、问答与预案（现场必答）

> 这一节不占主线时间，只在客户追问时用。ATP 是接单前的交期应答，不写主计划，和甘特不是同一套题面。

### 4.1 ATP 日期和主计划甘特对不上（必答）

**客户会怎么问**
> “同一张单，ATP 给的是 11-25，甘特上排到 11-27，到底哪个算数？是不是算错了？”

**一句话口径**：ATP 回答的是“现在这个只读题面下，最早哪天能做出来”；主计划回答的是“按策略权重正式排进去以后，这张单排在哪天”。两套口径，不是同一个数。

**必须讲清的三件事**

1. **ATP 的日期不是主计划的承诺日期。** ATP 是只读应答：`mainPlanWritten=false`，不写 `task / plan_version / solve_task`，也不改订单。它只告诉你“在这个题面下可行”；主计划的日期来自策略配置里的软权重（交期、换型、负载、最小制造周期等），由正式排产求解得出。ACCURATE 档固定按 `MIN_MAKESPAN=20` 加其余 7 条默认权重求解，权重和主计划不一定同源，日期自然可能不同。
2. **ATP 的题面比主计划窄，所以通常偏乐观。** 只按工艺路线做单层工序推演，不按 BOM 展开子件需求、不生成采购或半成品补库；不读在制报工；历史占用只取 BASELINE 已排任务这一层快照，`FROZEN` 按不可动处理，不做历史回放。ACCURATE 还有 7 天求解窗口，超出窗口的需求会表现为不可行、不给日期。题面少一层约束，日期就容易早一点。
3. **两边不一致时，正确回答是“这是两套口径，不是 bug”。** 不要现场改口径去凑数，也不要说“ATP 算错了”。如果客户追问 `VERIFIED` 的含义：`VERIFIED` 只代表该日期在这个题面下可行，是可行上界，不是最优性证明。

**台词（可照读）**
> “ATP 是接单前的快答，只读，不占产能、不改主计划；它给的是‘在我当前看到的这道题里，最早哪天做得出来’。主计划是把订单真正排进机台以后的结果，日期受策略里的交期、换型、负载这些权重影响。ATP 的题面更窄：只走单层工序，不展开 BOM 的用料需求，不读在制报工，历史占用也只看到已排任务这一层，所以它通常偏乐观。两边日期不一样，是两套口径，不是系统算错了。`VERIFIED` 只说明这个日期在当前题面下可行，是可行上界，不是最优性证明。”

**不要说**
- “ATP 的日期就是承诺日期。”
- “以 ATP 为准，甘特是错的。”
- “两边不一致是 bug，我回去查。”
- “`VERIFIED` 就是最优解。”

**如果客户要求“把 ATP 的日期直接落到主计划”**
> “ATP 只给建议，不写计划。要以这个日期承诺，得先确认订单，再走正式排产和产能锁定；ATP 返回的 `capacityLockSuggestion` 只是建议锁定哪些资源时段，`advisoryOnly=true`，不会自己落库。”

### 4.2 ATP 两个档位怎么选、超时怎么讲

| 档位 | `accuracy` | 现场体感 | 什么时候用 | 失败时 |
|---|---|---|---|---|
| `FAST` | 恒为 `ESTIMATE` | 亚秒级（P95 < 2 秒，不启动求解器） | 接单现场先给“大概哪天”，或客户一次问很多张 | 估算仍给日期，但明确是估算 |
| `ACCURATE` | 完整可行解才 `VERIFIED`，否则 `UNVERIFIED` | 十秒级（默认 10 秒，`timeoutSeconds` 可设 1–30） | 客户要一个“能兑现的日期”，单张单深算 | 超时返回 `TIMEOUT + UNVERIFIED`，**不给日期** |

**演示口径**
- 两档都演时，先说清楚：FAST 是估，ACCURATE 是验；两者可能一致也可能不一致，以当前题面结果为准，不是保证。
- ACCURATE 超时（网络、负载、求解窗口不够）时，**不要说“算不出来”**。正确说法是：
> “系统拒绝给不靠谱的日期。`TIMEOUT` 状态配 `UNVERIFIED`，日期字段是空的——宁可不给，也不编一个精确日期。这是产品设计，不是缺陷。”
- 客户问“那多久能给”：如实说默认 10 秒上限；要继续算就调 `timeoutSeconds`（最大 30 秒）重试，或先用 FAST 给一个估算区间，再让计划员走正式排产确认。
- 客户问“为什么 ACCURATE 还会超时”：题面里有既有负荷和 7 天窗口，限时求解没拿到完整可行解就不会标 `VERIFIED`。这时可以看 `bottlenecks[]`（如 `SOLVE_TIMEOUT`、`RESOURCE_QUEUE`）解释卡在哪，不要现场承诺“再等一会一定出”。

**台词（可照读）**
> “ATP 有两个档。FAST 是亚秒级的估算，适合接单时先给个大概；ACCURATE 是限时十秒的求解验证，只有拿到完整可行解才标 `VERIFIED`。如果十秒内没算完，系统会明确返回超时，并且不给日期——它不会为了好看编一个日期出来。您可以理解为：系统拒绝给不靠谱的日期，这是设计取舍。”

### 4.3 版本任务数 vs 场景任务数（必答）

**客户会怎么问**
> “你的计划里到底几个任务？版本详情写 32 条，甘特上怎么是 48 条？”

**口径**

1. `GET /plans/{id}` 里的 `taskCount` 是**该版本发布时固化的快照任务数**，历史快照，不可变。甘特（订单甘特 / 资源甘特）显示的是**场景当前工作集任务数**，走 `task` 表、不看 `plan_version_id`，会随重排、插单、任务调整变化。同一场景下这两个数字天然可以不同，本环境实测“首版 32 条、第二版 48 条、甘特 48 条”。
2. 差距来源是**本次发布只固化了自己范围内的订单**；范围外的任务仍留在场景里、没有绑定这个版本，**不是丢数据**。契约 C24 已冻结该语义，并明确“两个口径不得互校”。
3. 现场话术：**“版本是拍照，甘特是现场”**。客户若问“为什么甘特比版本多”，回答“因为版本只固化了这次发布的订单范围，其余订单还在场景里等下一次发布”。
4. **不要说**：“系统数据不一致”、“任务丢了”。

**台词（可照读）**
> “版本详情里的任务数，是发布那一刻拍下来的快照，发布后就不再变；甘特看的是这个场景现在的工作集，插单、重排、调任务都会让它变。一句话：版本是拍照，甘特是现场。数字对不上，通常是因为这次发布只固化了它范围内的订单，其余订单还留在场景里等下一次发布，不是数据丢了。契约里这两个口径本来就不互相校验。”

**客户追问“那到底以哪个为准”**
> “承诺和事后追溯看版本快照；看现场排产看甘特。要比就比同一版本的两份快照，不拿版本任务数和甘特任务数互校。”

**演示建议**
- 第 9 段打开版本详情时，如果客户同时看过甘特，主动把“版本是拍照，甘特是现场”这句说出来，不要等客户发现数字对不上再解释。
