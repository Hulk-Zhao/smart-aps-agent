# AI 辅助功能产品规划

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 日期 | 2026-11-05 |
| 状态 | 规划稿，可直接拆解为开发任务 |
| 范围 | AI 辅助能力的用户行为、入口、证据、失败态、首版范围 |
| 非范围 | 不写代码、不改前端、不改接口契约、不动 `docs/api/*`；不规划与 AI 辅助无关的模块 |

本文所有能力判断以仓库现状为准：4 个 Agent 端点当前全部返回 501，请求体 `JsonNode` 从未被读取，全仓无 HTTP 客户端与 LLM 配置。

---

## 0 结论

**MVP 只做「确定性解释」一个能力，覆盖三种形态：单次求解归因（含受影响任务下钻）、择优说明、场景对比说明；4 个 Agent 端点全部保持 501；首版不接模型、不做对话、不做单任务入口、不做自动重排。**

原因：`constraint_justification` 已持久化扣分明细，`scoreHard/scoreSoft`、`metrics.unassignedTaskCount`、`degraded` 与沙箱对比都有实数，足以回答计划员最高频的「这次为什么排成这样 / 两个版本差在哪」。相反，`nl-to-dsl` 受「DSL 尚未被求解读取」阻塞，`whatif` 的可注入变量不完整，`events` 没有任何事件来源；先做这三个端点只会增加占位或伪 AI。单任务入口也不在首版：甘特页只有 `sandboxId`，没有 `solveTaskId`，无法稳定回答「这条任务属于哪次求解」，先做会串场景。模型只作为后续可选的「改写措辞」，不作为事实来源。

## 1 能力盘点与诚实分级

### 1.1 判定所依据的事实

| 事实 | 对产品判断的影响 |
|---|---|
| `POST /agent/events`、`POST /agent/nl-to-dsl`、`GET /agent/explain/{taskId}`、`POST /agent/whatif` 均为 501 占位，请求体未读取 | 这 4 个端点不能作为「已有 AI 能力」对外宣传；任何入口先显示的能力必须是真能用的 |
| 全仓无 HTTP 客户端、无 LLM 端点或密钥配置 | 任何模型能力都要从零建设，必须有配置开关与失败文案；首版不接模型最稳 |
| `constraint_justification` 持久化 `constraintCode`、`type`（HARD/SOFT）、`taskIds`、`description`、`weight`、`deduction` | 解释可以完全由结构化证据生成，不依赖模型 |
| `SolveTaskDetail` 有 `scoreHard`、`scoreSoft`、`metrics.unassignedTaskCount`、`degraded`、`metrics.engineFallbackReason`、`engine`、`finishedAt` | 能区分「不可行」与「优化取舍」，能标注降级求解，不能把降级结果当正常基线比较 |
| 沙箱支持 `POST /sandboxes`（只允许 WHAT_IF，深拷贝父场景 snapshot，不复制任务）、`/{id}/apply`（幂等键必填、需要发布权限）、`/{id}/compare`（方向固定 `id - targetId`，返回交期差、利用率差、换型次数差、增删移任务数与前 200 条明细） | 结构化推演有确定性底座；但资源、日历等主数据级假设没有沙箱级覆盖入口，不能承诺「少一台设备」这类推演 |
| 约束 DSL 有「校验→创建→激活→回滚」完整生命周期（8 条规则白名单、权重合计 100、错误码 42201–42207），但 `ScheduleService` 不读取激活的 DSL 作为求解输入 | 自然语言生成 DSL 目前不会改变排产结果；做出来就是「看起来能改、实际不改」的伪能力 |
| 前端已有 19 个路由场景的悬浮帮助面板，每场景 4 段（定位、关键字段、操作顺序、常见错误） | AI 入口不得与帮助面板合并，也不得再增加第二个全局悬浮入口 |
| 统一错误码已有 40000/40100/40300/40400/40900/40901/40903/42200/42201/42900/50000/50010/50100/50300；DSL 明细码为 42201–42207 | 失败态全部复用现有码，不新造码；主文案不直接甩码 |
| 现有 3 个 Agent 写端点带 `AGENT_EVENT` 权限，`GET /agent/explain/{taskId}` 无权限注解 | 解释读取需要先明确读权限归属，否则一旦接入数据会扩大可读面 |

### 1.2 四端点判定表

| 端点 | 不需要模型能做的事 | 必须模型才能做的事 | 判定 | 首版动作 |
|---|---|---|---|---|
| `POST /agent/events` | 事件类型已是固定枚举，登记、影响面查询、触发沙箱增量求解都可以是确定性的 | 无。这不是语言任务 | **当前不应实现** | 保持 501 |
| `POST /agent/nl-to-dsl` | 无。把中文翻译成 8 条规则及权重是语言任务 | 自然语言→DSL 及参数映射 | **当前不应实现**（若解除 DSL 阻塞，则属「需模型增强」） | 保持 501 |
| `GET /agent/explain/{taskId}` | 用归因、分数、未排数、降级标记组装「原因+证据+建议」 | 自由追问、长文摘要、跨多次求解的归纳 | **确定性可实现（无需模型）**；但契约缺少求解基准 | MVP 用现有读接口组合，端点保持 501 |
| `POST /agent/whatif` | 复制场景、运行求解、对比结果（确定性推演流程） | 把一句自然语言问题解析成可执行参数 | **需模型增强**；MVP 不实现 | 保持 501；P1 做结构化推演向导 |

### 1.3 逐条判定理由

#### 1.3.1 `POST /agent/events`：当前不应实现

- 请求里的 `eventType` 已经是 `EQUIPMENT_DOWN / MATERIAL_SHORTAGE / ORDER_RUSH / CAPACITY_ABNORMAL` 四值枚举，分类不需要模型。也就是说这个端点从技术上看不是 AI 能力，而是「事件接入 + 影响评估」的集成能力。
- 仓库没有事件存储、事件消费者、事件页面，也没有 MES 等上游事件源。现在实现只能做成一个「收下请求就丢掉」或「直接触发一次增量求解」的空壳。
- 「局部微调还是全局重排」的决策矩阵没有定义阈值与责任人。把没有定义的决策交给自动流程，等于把排产权交给一个没人能解释的规则。
- 正确顺序是：先有事件源与事件登记表，再谈影响评估；两者都不具备时，保持 501 是最诚实的状态。

#### 1.3.2 `POST /agent/nl-to-dsl`：当前不应实现（解除阻塞后属需模型增强）

- 这是四个端点里最典型的模型任务：产出物本身就是一段 DSL 文本，8 条规则的权重与白名单参数需要从中文语义映射。
- 但它有一个结构性阻塞：DSL 虽已能校验、激活、回滚，**求解并不读取激活的 DSL**。模型生成得再准，也不会改变任何一次排产结果。
- 第二重阻塞是收益问题：规则只有 8 条、权重必须合计 100、参数有白名单，配置人员用表单本来就能完成；自然语言带来的便利不足以抵消一次误译的代价。
- 第三重风险是误译后果：权重错 5 分不会报错，只会让结果悄悄变差。用户无法从结果反推「是模型翻错了」。
- 结论：只有当 DSL 真正成为求解输入，并且出现「配置人员不会填表但会描述业务规则」的真实需求后，才进入 P2 评估。

#### 1.3.3 `GET /agent/explain/{taskId}`：确定性可实现，但首版不实现该端点

- 解释所需的一切都已在库里：约束编码、硬/软类型、权重、扣分、受影响任务、朝向人的描述；再加求解分数、未排任务数、是否降级、引擎与完成时间。
- 因此可以完全不用模型，按固定模板生成三段：结论、按扣分排序的原因、证据引用。模型最多把「MIN_TARDINESS 权重 20 扣 240 分」改写成更顺的一段话，不参与事实判断。
- **但不建议在首版实现这个端点**，原因是契约缺口：路径只有 `taskId`，而归因是按 `solve_task` 持久化的。同一个任务可能出现在多次求解、多个沙箱里，端点无法知道该用哪一次结果；默认取「最近一次」会把 A 场景的解释安到 B 场景的头上，这是最坏的一类可信度事故。
- 首版因此采用「上下文解释」：用户在某个求解结果的上下文里点开，就用该结果的 `solveTaskId` 和 `justifications`；求解详情与归因两个 GET 已足够，不需要改契约。
- 另外，该端点当前没有权限注解。解释会暴露订单、任务、约束权重，必须先明确读权限（建议复用求解详情的读权限），不能默认匿名。

#### 1.3.4 `POST /agent/whatif`：需模型增强

- 契约要求 `sandboxId + question`，也就是先有一句自然语言。没有模型时只能做模板匹配（例如固定句式「订单 X 延后 N 天」），覆盖面和鲁棒性都不足以上线。
- 但「假设→运行→对比」的底座是确定性的：创建 WHAT_IF 场景、在该场景求解、用 `compare` 取差异。用户真正需要的动作并不依赖对话。
- 首版因此不做这个端点，也不做聊天框；P1 用结构化表单覆盖同一用户任务。P2 再评估「一句话→参数预览→人工确认→运行」的对话形态。
- 必须提前承认能力边界：现有接口可注入的假设主要是订单范围、策略、求解参数；资源减少、日历调整等主数据级假设没有沙箱级入口。不能在产品文案里承诺这些推演。

### 1.4 可复用的证据底座

| 证据 | 来源字段 | 可回答的问题 | 已知缺口 |
|---|---|---|---|
| 求解结果 | `SolveTaskDetail.taskId/status/scoreHard/scoreSoft/metrics.unassignedTaskCount/degraded/metrics.engineFallbackReason/engine/finishedAt` | 这次求解可不可行、优化得好不好、是否降级 | 分数是汇总值，不能单独定位到任务 |
| 约束归因 | `ConstraintJustification.constraintCode/type/taskIds/description/weight/deduction` | 哪些约束扣了分、扣了多少、影响哪些任务 | `taskIds` 可能为空，只能给「约束级」证据；硬约束 `deduction` 恒为 0 |
| 场景对比 | `SandboxCompareView.dueDateDeltaMinutes/utilizationDelta/setupCountDelta/addedTaskCount/removedTaskCount/movedTaskCount/changedTasks/truncated` | 两个场景差了多少、哪些任务增删移 | 只有计数与前 200 条明细；版本级约束归因需要先稳定定位两侧求解，当前不具备 |
| 当前任务 | `GET /gantt/order` 的任务条字段 `taskId/orderNo/resourceCode/startTime/endTime`（前端类型 `GanttTask.id`） | 被影响的任务具体是哪几条、当前在哪台资源上 | 必须按 `sandboxId` + 时间窗查询；这是当前场景状态，求解后人工调整会改变时间，必须标注 |

**由此产生的第一条产品铁律：** 解释只能陈述证据能覆盖的事实。没有 `taskIds` 时禁止说「这个任务被扣了 X 分」；只能显示「该约束整体扣 X 分，未记录到具体任务」。硬约束不允许包装成「优化取舍」。

## 2 场景优先级

### 2.1 场景总表

| ID | 优先级 | 用户 | 页面 | 什么时候会点 | 不用它会怎样 | 用了之后少做什么动作 |
|---|---|---|---|---|---|---|
| P0-1 | P0 | 计划员、计划主管 | `/solve-tasks` 结果区 | 求解完成但软分为负、有未排任务、或降级，想确认主因 | 只看到一个总分；打开甘特逐单看，也不知道是换型、交期还是权重；找开发查库 | 少做「逐单翻任务、导出比对、询问开发、盲改权重重排」 |
| P0-2 | P0 | 计划主管、评审人 | `/solve-tasks` 结果区（同一面板下钻） | 看到前 5 条主因后，需要知道到底影响了哪些订单/任务 | 只能按约束编码自己猜影响范围，或去甘特一屏屏找 | 少做「按编码猜范围、跨页搜订单、手工统计受影响任务」 |

| P1-1 | P1 | 计划员 | `/gantt-orders` 选中任务详情区 | 看到某条任务晚交、被移到非预期资源、或未排上，想只问这一条 | 只能回到求解结果总览里按任务号找，或凭经验猜 | 少做「按任务号回查、跨页对照、询问计划主管」；前置条件是能稳定定位该任务所属的求解记录 |

| P1-3 | P1 | 计划主管 | `/solve-tasks`、`/plans/compare` | 归因条目超过 8 条，需要一段可转述的结论 | 自己读十几条约束再组织语言，评审材料靠手写 | 少做「逐条读、手工整理汇报口径、复制粘贴证据」 |
| P1-4 | P1 | 全部解释使用者 | 解释面板 | 解释与事实不符，或看不懂 | 私下吐槽或找开发，问题无法沉淀 | 少做「截图、描述复现、重复反馈同一问题」 |
| P2-1 | P2 | 排产策略配置人员 | `/strategies` | 客户用口语描述规则，配置人员需要落成 8 条规则权重 | 手工试权重，或者干脆不配 | 少做「反复试权重、口头确认语义」；仅当 DSL 接入求解后才成立 |
| P2-2 | P2 | 车间调度、计划员 | 暂无页面（需先有事件源与事件列表） | 设备停机、缺料、急单插入 | 电话通知、人工判断影响面、手工挑选受影响订单 | 少做「人工圈订单、逐个判断影响、重复发起重排」；仅当事件源存在后才成立 |
| P2-3 | P2 | 计划员 | `/sandbox` | 口头假设无法直接落到参数，例如「如果 A 客户插单会怎样」 | 需要自己把话翻译成订单范围与策略，容易漏条件 | 少做「手工翻译假设、反复试参数」；必须先解析成参数预览并人工确认 |

### 2.2 P0 场景展开

**P0-1 单次求解归因**

- 用户任务：判断这次求解的主要矛盾，决定是调策略、补主数据，还是接受现状。
- 入口触发条件：求解终态后入口常驻但收起，用户主动点击「解释本次结果」；不因分数健康而隐藏（安静可用即可，不自动展开）。
- 完成判据：按扣分从大到小给出前 5 条原因，明确「不可行」与「优化取舍」的区分；显示未排任务数、硬分与降级原因。
- 不做的边界：不解释求解器内部搜索过程；不自动建议改哪条权重；没有 `taskIds` 时不把原因说成「某条任务被扣分」。

**P0-2 受影响任务定位**

- 用户任务：在 P0-1 的面板里看到主因后，确认这条约束到底压到了哪些订单/任务，决定是否打开甘特核对。
- 入口触发条件：P0-1 面板内展开某一条原因；只在 `justification.taskIds` 非空时提供。
- 完成判据：用 `detail.sandboxId` 与 `detail.tasks` 的起止窗口调用 `GET /gantt/order`，按 `taskIds` 匹配任务条 `taskId`（前端 `GanttTask.id`），展示订单号、资源、起止时间，最多 20 条；超出折叠为「查看全部 N 条」；清单标题固定标注 `当前场景状态`，提示「若求解后有人工调整，时间可能已变化」。`taskIds` 为空或 `detail.tasks` 为空时显示「未记录到具体任务」。
- 不做的边界：首版不做「单任务入口」；不做跨求解任务的定位。原因：甘特页当前只持有 `sandboxId`，没有 `solveTaskId`，无法稳定判断一条任务属于哪次求解；把最近一次当答案会串场景。单任务归因列入 P1-1。

**P0-3 版本/场景差异说明**

- 用户任务：理解多策略择优为什么推荐这一版；在沙箱里理解两个场景到底差在哪。
- 入口触发条件：`/plans/compare` 已返回 `items` 与 `recommendedPlanId`；`/sandbox` 已返回 `compare`，且两侧均有任务（未求解的沙箱只显示「尚未产生对比结果」）。
- 完成判据：
  - 择优：显示推荐版本的 `scoreHard`、`scoreSoft`、`taskCount`，以及其他版本相对推荐版的差值与 `tieBreak`（按字面量翻成「硬分降序 → 软分降序 → 计划 ID 升序」）；硬分不同的版本明确标「不可行差异」，不比较软分高低；分数为 `null` 的版本显示「无分数」，不按 0 计算。
  - 沙箱：显示 `dueDateDeltaMinutes`、`utilizationDelta`、`setupCountDelta` 三个差值与方向，给出增删移计数与前 20 条 `changedTasks`；`truncated = true` 时提示「明细已截断，计数为全量」。
- 不做的边界：计划版本与求解任务之间没有直接外键，现有对比按「同租户+同场景+发布前最后一次 SOLVED」定位求解记录，属于推断基准。首版不拿这个推断去贴约束归因；「版本级约束扣分差」留到后续评估，且必须先把定位规则产品化。不得用模型补原因。

### 2.3 P1/P2 的进入门禁

| 能力 | 进入下一阶段的必要条件 |
|---|---|
| P1-1 单任务归因（甘特） | 能稳定定位「选中任务 → 产生它的 solveTaskId」；不能靠最近一次猜；入口只在定位成功时出现 |
| P1-2 结构化推演 | 明确可注入变量清单；推演场景不落到正式基线；对比结果能在同一页面闭环 |
| P1-3 模型摘要 | 模型服务与数据合规决策完成；解释证据覆盖率可接受；摘要中的每个数字可回指证据 |
| P1-4 反馈闭环 | 反馈存储、查看权限、保留期限确定；反馈不得自动改权重或计划 |
| P2-1 NL→DSL | DSL 真正成为求解输入；有真实配置人员需求；生成结果强制预览、校验、沙箱验证 |
| P2-2 事件感知 | 有 MES/上游事件源；有事件登记与生命周期；局部/全局阈值与责任人明确 |
| P2-3 对话式 what-if | P1-2 已稳定；模型只产出参数预览，必须人工确认后才运行 |

## 3 简洁性原则

这一节是硬规则，开发可直接按编号实现与验收。目标不是「看起来克制」，而是可验证的不打扰。

### 3.1 三条底线

- **C-01 不新增全局入口。** 不新增右下角悬浮球、侧栏菜单项、顶栏图标、页面级聊天框。解释入口只挂在被解释对象旁边：首版是求解结果区与对比结果区，P1 才是甘特选中任务。
- **C-02 不主动出现。** 页面加载、数据刷新、求解完成、切换沙箱、切换版本、选中任务，都不得自动打开解释面板。唯一打开方式是用户点击。
- **C-03 不推送、不计数。** 不做红点、角标、未读数、toast、横幅、声音、脉冲动画。解释是「按需查询」，不是通知。

### 3.2 入口矩阵

| 页面 | 锚点 | 固定文案 | 默认状态 | 打开形态 |
|---|---|---|---|---|
| `/solve-tasks` 结果区 | 结果区标题右侧 | `解释本次结果` | 收起 | 右抽屉 |
| `/gantt-orders` 选中任务详情区（P1） | 详情区标题右侧文字链 | `查看归因` | 收起 | 右抽屉（挤压布局，不浮层覆盖）；首版无入口 |
| `/gantt` 资源甘特 | 无入口 | — | — | — |
| `/plans/compare` | 指标区标题右侧 | `解释差异` | 收起 | 结果区下方内联展开 |
| `/sandbox` 对比结果 | 对比区标题右侧 | `解释差异` | 收起 | 结果区下方内联展开 |
| `/strategies` | 无入口（NL→DSL 未实现） | — | — | — |
| `/`、`/orders`、`/mrp/analysis`、`/import`、主数据、系统页 | 无入口 | — | — | — |

补充规则：

- 求解入口只在结果终态时出现；无归因时仍可点开，给空态，不隐藏、不猜。
- 表格内不新增「AI」列；入口放操作列，或复用已有的展开行。P1 的甘特任务入口只在能定位到求解记录时出现，否则显示 `查看归因（无记录）`。
- 甘特资源视图是只读核对页，首版不放解释入口，避免每个任务条都挂一个入口造成视觉噪音。

### 3.3 默认态与生命周期

- **C-04 单实例。** 同一时刻最多一个解释面板。打开第二个对象时替换内容，不叠两个；切换路由立即关闭。
- **C-05 不记忆。** 刷新、重新进入页面一律收起；不做「不再提示」「上次打开过就自动展开」；不对用户做打开状态持久化。
- **C-06 不抢焦点。** 打开面板不改变当前选中对象、不滚动页面、不改变甘特缩放、不改变表格排序与筛选。仅在用户从证据点击任务时做一次定位滚动。
- **C-07 关闭可预期。** `Esc` 关闭；关闭后焦点回到触发元素；点击其他对象不关闭面板，但会把内容切换到新对象（若新对象无证据则显示空态），切换前不弹确认。

### 3.4 什么时候不该出现

以下条件命中时，入口隐藏或置灰，且不显示任何解释性浮层：

1. 求解状态为 `PENDING` 或 `RUNNING`，证据尚未定稿；只有终态结果才显示入口。
2. 没有可解释对象：求解未完成、未选中两个版本、对比结果尚未返回。
3. 用户正处于任务调整、发布确认、沙箱应用、导入确认等弹窗中。
4. 用户正在拖拽甘特任务条，或正在编辑表格单元格。
5. 当前视图是打印预览、导出预览、只读快照。
6. 当前账号无该求解结果的读权限，或跨租户不可见。
7. 模型未配置时，只隐藏「AI 解读」区块，保留确定性归因入口；不得因此隐藏整个入口。
8. 同一对象已有请求在途，按钮进入 loading；不允许并发重复请求。

### 3.5 密集页面不遮挡数据的规则

甘特专用规则（C-08 至 C-10、C-13、C-14）随 P1-1 落地；首版 `/solve-tasks`、`/plans/compare`、`/sandbox` 按 C-11、C-12 的表格规则执行。

- **C-08 图表用挤压，不用浮层。** `/gantt-orders` 打开解释时，右侧抽屉占 360px（≥1440 宽）或 320px（1280–1439 宽），由布局压缩图表可用宽度；不得用悬浮卡片压住任务条、交期线或资源行标题列。
- **C-09 不改用户视图。** 打开抽屉不自动改变缩放档位、不自动跳到别的日期、不重置图层开关。仅在用户点击证据任务时定位一次；定位后不再自动滚动。
- **C-10 窄屏退让。** 视口小于 1280px 时改为底部抽屉，最大高度 45vh，可拖拽收起；不得居中弹窗，不得加遮罩。窄屏下甘特页优先只展示「结论 + 前 3 条证据」，其余折叠。
- **C-11 表格不挤压关键列。** 表格页不新增列、不缩小已有列；解释用右抽屉或结果区下方内联，均不得遮挡订单号、资源、时间这四个关键列。计划对比与沙箱对比按内联展开，不额外挤压列宽。
- **C-12 单元格不承载句子。** 表格单元格只允许确定性短标签（如 `晚交`、`未排`、`降级`），不得放模型生成的句子；长内容一律进解释区（抽屉或结果区内联）。
- **C-13 不新增悬浮提示。** 密集页禁用多行 tooltip；不新增「悬停即解释」。解释必须由点击进入解释区。已有的图表原生提示不受影响。
- **C-14 一次只显示一个锚点。** 甘特不在每个任务条上放按钮；入口只出现在当前选中任务的详情区。

### 3.6 与帮助面板的边界

- 帮助面板回答「这个页面怎么用」，解释面板回答「为什么是这个结果」。两者入口分离：帮助仍是右下角悬浮入口，解释在对象旁。
- 不合并成一个大聊天窗，不让帮助面板出现「问我任何问题」输入框。
- 解释面板最多提供一个文字链 `查看页面帮助`，跳转到现有帮助内容；反向不做强制跳转。
- 帮助面板已有的 19 个场景不因本功能增删；解释入口不得占用帮助面板的快捷键或位置。

### 3.7 可验收的简洁性检查

| 编号 | 检查项 | 通过条件 |
|---|---|---|
| V-01 | 首屏干扰 | 任意页面首次加载，没有任何解释面板、红点、角标、toast 自动出现 |
| V-02 | 入口数量 | 每个支持页面最多一个解释入口；甘特每个任务条 0 个常驻按钮 |
| V-03 | 单实例 | 连续打开两个对象，DOM 中只有一个解释面板 |
| V-04 | 不遮挡 | 打开面板后，表格关键列与指标区仍完整可见；P1 甘特任务条与交期线同样不被遮挡 |
| V-05 | 视图稳定 | 打开/关闭前后，表格排序筛选与滚动位置不变；P1 甘特缩放档位不变（定位动作除外） |
| V-06 | 刷新复位 | 刷新页面后面板为收起状态 |
| V-07 | 键盘 | `Esc` 可关闭，焦点回到触发元素 |

## 4 可信度设计

### 4.1 双层结构：证据在前，解读在后

解释面板固定分两块，顺序不可颠倒：

1. **证据（确定性）**：只放来自字段的数字与短句，带来源标签。默认展开。
2. **AI 解读（可选）**：只有模型可用且用户已主动请求时出现；默认不请求、不预取。模型不可用时整块不显示，不留空白占位。

禁止把「事实」和「模型推断」写在同一段。禁止模型改写证据区的数字。

### 4.2 证据来源标注

每条证据固定格式：

```text
MIN_TARDINESS（软约束，权重 20）扣 240 分 · 影响 8 个任务
来源：约束归因 · solve#1234
```

| 展示内容 | 必填来源标签 | 数据字段 |
|---|---|---|
| 硬分、软分 | `求解结果` | `scoreHard`、`scoreSoft` |
| 未排任务数 | `求解结果` | `metrics.unassignedTaskCount` |
| 引擎降级与原因 | `求解结果` | `degraded`、`metrics.engineFallbackReason` |
| 约束名称、类型、权重、扣分 | `约束归因` | `constraintCode`、`type`、`weight`、`deduction` |
| 受影响任务 | `当前任务` | `taskIds` 与 `GET /gantt/order` 任务条的 `taskId`（前端 `GanttTask.id`）；标注当前场景状态 |
| 交期差、利用率差、换型差 | `场景对比` | `dueDateDeltaMinutes`、`utilizationDelta`、`setupCountDelta` |
| 增删移任务 | `场景对比` | `addedTaskCount`、`removedTaskCount`、`movedTaskCount`、`changedTasks` |

规则：

- **T-01 数字必须有字段。** 界面上出现的每个数字都要能指到上表某一字段；计算得出的数字（如扣分占比）必须标注「计算值」并给出公式。
- **T-02 无任务明细就说约束级。** `taskIds` 为空时，禁止写「这条任务被扣分」；只能写「该约束整体扣分，未记录到具体任务」。
- **T-03 排序稳定。** 原因按 `deduction` 降序，再按 `weight` 降序，再按 `constraintCode` 升序；默认展示前 5 条，其余折叠为「查看全部 N 条」。
- **T-04 硬软分开。** 硬约束违背（`scoreHard != 0` 或 `unassignedTaskCount > 0`）必须单独置顶，文案是「未满足硬约束/未排任务」，不得说成「优化取舍」；硬约束的 `deduction` 为 0，不参与软约束排序。若没有可识别的硬约束归因（`type = HARD` 且无 `taskIds`/扣分证据），只显示「硬约束未满足，归因未记录具体条目」，不得把软约束说成不可行的原因。
- **T-05 降级必须提示。** `degraded = true` 时，解释顶部固定提示「本次为降级求解（原因：{engineFallbackReason}）。分数与归因可能与其他结果不可比。」
- **T-06 基准必须可见。** 面板底部固定显示「本解释基于求解任务 #1234（完成于 …）。之后的重新求解或人工调整不会自动更新本解释。」
- **T-07 对比方向必须说人话。** 场景对比统一标注「推演相对基线」；交期超期变多为「更差」，利用率变高为「更高」，换型次数变多为「更多」。不得只用正负号或只用颜色。

### 4.3 确定性摘要的生成规则

不接模型时，摘要按固定模板填充，缺字段就删句子，不允许补写：

```text
本次求解软分 {scoreSoft}，主要来自 {N} 条软约束。
最大扣分是 {constraintCode}（权重 {weight}，扣分 {deduction}，影响 {taskIds.length} 个任务）。
未排任务 {unassignedTaskCount} 个。
```

- 上述每个占位符必须有值才输出；`taskIds` 为空时改写成「影响范围未记录到具体任务」。`N` 只统计 `deduction > 0` 的软约束，不把零扣分约束算进「主要来自」。
- 没有归因记录时，摘要固定为「该求解任务没有可用的归因记录」，原因区为空，建议只保留「可重新求解以生成归因」。
- 建议区只允许三类确定性建议：`重新求解以生成归因`、`查看受影响任务`、`查看求解详情`。不得出现「建议调整 XX 权重」这类模型式建议。

### 4.4 模型生成内容的标注

- **T-08 固定标签。** 每个模型段落前必须有 `AI 解读` 标题，段尾必须有 `以上为 AI 生成内容，可能有误；事实以「证据」区为准。`
- **T-09 标签不可关闭。** 用户不能设置隐藏 AI 标签；导出、复制、截图说明中同样保留。
- **T-10 复制即带标签。** 复制 AI 段落时自动追加 `[AI 生成，仅供参考]`；复制证据段落时不加。
- **T-11 模型不碰数字。** 模型只能引用证据区已存在的数字与编码；生成结果必须做数字校验：出现证据中不存在的数字，整段丢弃并回退到「AI 解读与证据不一致，已隐藏」。不得只删数字留下句子。
- **T-12 不展示置信度百分比。** 不用「置信度 85%」这类伪精度；只用 `依据完整` / `依据不足` 两档，依据完整度由「有扣分明细的约束条数」决定，规则固定。
- **T-13 不流式先显示。** 模型内容必须完成数字校验后才一次性展示；不允许边生成边渲染。
- **T-14 空值不等于 0。** `scoreHard`、`scoreSoft` 为 `null` 时显示「无分数」，不参与差值计算与排序展示；不得把缺失值渲染成 0。`taskCount` 是必填整数，不存在空值。
- **T-15 证据可定位到条目。** 每条归因以 `solveTaskId + constraintCode` 作为引用键，格式 `source=solve:{solveTaskId}#{constraintCode}`；同一编码若出现多条，追加 `deduction` 与 `taskIds` 摘要区分。不得出现只有「某约束扣分」而没有引用键的句子。

### 4.5 模型不可用与降级文案

以下文案可直接进入实现，位置固定。

| 场景 | 位置 | 用户可见文案 | 行为 |
|---|---|---|---|
| 未配置模型 | AI 区块位置 | `AI 解读未启用（管理员未配置模型服务）。下方为求解结果中的原始归因，可正常使用。` | AI 区块折叠为一行说明，不显示请求按钮的报错 |
| AI 入口禁用 | 按钮 tooltip | `AI 解读未启用` | 按钮置灰，可聚焦读屏 |
| 模型超时 | AI 区块 | `AI 解读超时（超过 15 秒）。原始归因不受影响，可重试。` | 保留证据区；提供 `重试`；连续 3 次失败后隐藏 AI 入口 10 分钟 |
| 模型服务异常 | AI 区块 | `AI 解读服务异常。原始归因不受影响，可重试。` | 同上；技术详情展示业务码与 traceId |
| 模型输出与证据不一致 | AI 区块 | `AI 解读与证据不一致，已隐藏该段内容。` | 整段丢弃，不用模型内容替代证据 |
| 解释记录缺失 | 证据区 | `该求解任务没有归因记录。归因由求解结果写入，早期求解可能没有记录。` | 显示空态；不请求模型；提供 `查看求解详情` |
| 降级求解 | 面板顶部 | `本次为降级求解（原因：{engineFallbackReason}）。分数与归因可能与其他结果不可比。` | 证据照常展示，AI 摘要禁止做跨版本比较 |
| 硬约束未满足 | 证据区置顶 | `本次求解未满足全部硬约束：硬分 {scoreHard}，未排任务 {unassignedTaskCount} 个。以下解释的是「为什么不可行」，不是「为什么这样优化」。` | 硬约束原因置顶，软约束在后 |

### 4.6 用户纠错与反馈

- 入口：解释面板底部固定文字链 `这条解释有误`。不放在显眼主按钮位，避免引导用户把解释当结论投票。
- 表单固定选项：`证据不对（约束/扣分/任务对不上）`、`结论与事实相反`、`漏掉了重要约束`、`看不懂/表述不清`、`其他`；备注最多 200 字，可选。
- 提交时随附证据快照：`solveTaskId`、约束编码列表、展示过的数字、用户、时间。不随附订单明细以外的业务数据。
- 提交成功文案固定：`已记录。该反馈不会自动修改排产结果、约束权重或计划版本。`
- 反馈不进入训练、不自动调权重、不自动改 DSL、不自动重排。只用于产品侧统计与人工复核。
- 用户认为解释不准时的即时自救路径：`收起 AI 解读`（证据仍在）、`查看求解详情`、`重新求解以生成归因`。不允许用户直接编辑解释文本，避免破坏审计。
- 本节为 P1 设计。首版 MVP 不提供反馈入口：没有模型时不存在「AI 说错」，为几条确定性证据单独建反馈表不划算；等 P1-4 再连同模型解读一起开放。

## 5 失败态清单

| 情形 | 触发条件 | 用户看到 | 业务码 | 恢复动作 |
|---|---|---|---|---|
| 无模型配置 | 模型能力未启用或配置缺失 | `AI 解读未启用（管理员未配置模型服务）。下方为原始归因，可正常使用。` | 50300（仅在调用模型接口时） | 继续用证据区；管理员配置后可重试 |
| 模型超时 | 模型调用超过 15 秒 | `AI 解读超时（超过 15 秒）。原始归因不受影响，可重试。` | 50300 | 重试；连续失败隐藏入口 10 分钟 |
| 模型返回不合规 DSL（仅 P2） | 生成结果未通过校验 | `生成的约束未通过校验，未保存，也未影响任何计划。` + 逐条问题清单 | 42200；明细 `issues[].code` 42201–42207 | 返回修改描述；不自动修复、不自动激活 |
| 解释信息缺失 | 该求解没有 `constraint_justification` | `该求解任务没有归因记录。` | 200（业务成功，无数据） | 重新求解以生成归因；或只看求解详情 |
| 沙箱运行失败 | 求解终态 `FAILED`，或引擎不可用 | `推演失败：求解引擎不可用。假设未产生结论，正式计划未受影响。` | 50010 | 重试推演；保留场景与参数；基线不动 |
| 沙箱运行超时 | 求解终态 `TIMEOUT` | `推演超时（已运行 {elapsedMs}）。正式计划未受影响。可缩小订单范围或延长时间后重试。` | 轮询结果为 200，任务状态 `TIMEOUT` | 缩小范围或调大时间上限后重试 |
| 沙箱任务含已执行任务 | 场景内存在 `IN_PROGRESS/COMPLETED` | `该场景包含已开工或已完成任务，不能整体重排。` | 40903 | 改用未执行任务子集或新建场景 |
| 沙箱已归档 | 对 ARCHIVED 场景 apply | `已归档场景不可应用。` | 40901 | 复制为新 WHAT_IF 后重试 |
| 并发修改 | 场景版本过期、计划版本被他人更新 | `数据已被他人更新，请刷新后重试。` | 40901 | 刷新重取；不覆盖他人改动 |
| 幂等键冲突 | 相同 `Idempotency-Key` 正在处理 | `该操作正在处理中，请勿重复提交。` | 40900 | 等待结果；不要换对象重试 |
| 已发布计划不可覆盖 | 对已发布版本执行覆盖/回滚 | `已发布的计划不可被覆盖，请走回滚或新建版本。` | 40903 | 新建版本或按版本回滚 |
| 任务/版本不存在 | 已删除、跨租户、ID 错误 | `找不到该任务或版本。` | 40400 | 返回列表重新选择 |
| 权限不足 | 无该求解结果读权限 | 入口不显示；若直接访问：`当前账号没有查看该结果的权限。` | 40300 | 申请权限；不提示资源是否存在 |
| 请求过于频繁 | 触发现有固定窗口限流 | `操作太频繁，请稍后再试。` | 42900 | 按钮禁用 30 秒；不做自动重试风暴 |
| 内部错误 | 未预期异常 | `解释暂时不可用，请稍后重试。` | 50000 | 重试；技术详情展示 traceId |
| 调用未实现端点 | 前端误调任一占位端点 | 不展示错误码，显示 `该能力尚未开放` | 50100 | 首版前端不得调用任一 501 端点 |

补充规则：

- **F-01 主文案不甩码。** 业务码只在 `技术详情` 展开区展示（`错误码 50300 · traceId …`），或 DSL 问题清单里作为括号说明；不允许只显示「50300」。
- **F-02 证据不随失败消失。** 模型失败、网络失败只影响 AI 区块；已加载的证据区保持可见。
- **F-03 不自动重试。** 42900、40901、50010 一律由用户点击重试；禁止后台静默重试产生额外求解任务。
- **F-04 不伪装成功。** 无归因时不得返回模型编的「原因」；沙箱失败时不得展示部分对比结果。
- **F-05 错误可追踪。** 所有失败态在技术详情展示 traceId；满足现有 `X-Trace-Id` 贯穿约定。

## 6 首版范围（MVP）建议

### 6.1 做

| 能力 | 形态 | 复用的真实数据 | 用户可见完成标准 |
|---|---|---|---|
| 单次求解归因 | `/solve-tasks` 结果区抽屉 | `GET /solve-tasks/{id}` + `GET /solve-tasks/{id}/justifications` | 一次点击看到前 5 条主因、硬分/软分、未排任务数、是否降级 |
| 受影响任务定位 | 同一抽屉内下钻 | 同上 + `GET /gantt/order`（按 `sandboxId` 与任务起止窗口） | 每条原因可展开受影响订单/任务（≤20 条，标注当前场景状态）；无 `taskIds` 显示「未记录到具体任务」 |
| 择优解释 | `/plans/compare` 内联区 | `items/recommendedPlanId/tieBreak` | 说清为何推荐这一版、分差多少、是否是硬分差异 |
| 场景对比解释 | `/sandbox` 内联区 | `compare` 三差值与 `changedTasks` | 三个差值方向 + 增删移明细；截断时明示 |

以上形态共用一套「证据组装」逻辑，不新增后端端点，不改契约。4 个 Agent 端点全部保持 501。

**为什么首版不实现 `GET /agent/explain/{taskId}`：** 路径只有一个 `taskId`，而归因按 `solve_task` 持久化；同一任务会出现在多次求解和多个沙箱中。缺少基准就实现，只能靠「取最近一次」猜，猜错会把别的场景的结论贴到当前任务上。这是可信度红线，不能用实现速度换。若后续确需该端点，必须先在契约层定义求解基准，这不属于本规划范围。

### 6.2 不做

| 不做项 | 理由 |
|---|---|
| `POST /agent/events` | 没有事件源、事件存储、事件页面；做了也是空壳 |
| `POST /agent/nl-to-dsl` | DSL 不参与求解，生成结果不改变排产；误译权重不会报错 |
| `POST /agent/whatif` | 契约要求自然语言问题；无可注入变量清单；对话会掩盖参数不确定性 |
| 任何模型调用 | 无模型配置与合规结论；事实已足够回答首版问题 |
| 自由文本输入 / 聊天框 | 会把「查证据」变成「许愿」，且增加注入面 |
| 自动生成调整建议 | 建议一旦被当成结论，用户会跳过核对；首版只给证据与确定性下一步 |
| 版本级约束归因差 | 版本与求解任务无外键，只能按推断基准定位；贴错原因比不给原因更伤可信度。留到后续评估并先产品化定位规则 |
| 反馈学习 / 自动调权重 | 无审计、无样本治理，容易形成不可解释的反馈回路 |
| 甘特单任务入口 | 甘特页只有 `sandboxId`，没有 `solveTaskId`，无法稳定定位归因；先做会串场景。列入 P1-1 |
| 全局面板 / 甘特任务条常驻按钮 | 违反第 3 节简洁性规则 |

### 6.3 交付前置条件

- 解释读取必须复用求解详情的读权限；当前 `GET /agent/explain/{taskId}` 无权限注解的问题不能带进新能力。
- 前端只调用已实现的求解详情、归因、甘特读、择优与沙箱对比 GET；不得为了「看起来有 AI」调用 501 端点或 mock 数据。
- 解释面板不修改现有帮助面板的注册表与 19 个场景。
- 所有文案以本文附录为准；新增文案必须能指到某个证据字段。

### 6.4 MVP 完成判据

1. P0-1/P0-2/P0-3 三个 P0 能力可达，且首次加载不自动出现。
2. 任意一条证据都能看到来源标签；没有 `taskIds` 时不出现「该任务被扣分」的表述。
3. 无归因、降级、硬约束未满足三种情况分别显示第 4.5 节规定的文案，不请求模型。
4. 4 个 Agent 端点状态与本文一致：全部 501，页面不调用。
5. 打开/关闭解释前后，所在页面的排序、筛选、滚动位置不变；抽屉不遮挡关键内容。
6. `Esc` 可关闭，焦点回到入口；刷新后收起。
7. 用真实种子数据走通一次「求解→解释→展开受影响任务」；无归因求解与空沙箱显示空态。

### 6.5 进入 P1 的门槛

- 模型服务与数据合规（供应商、区域、数据留存）有明确结论；该门槛只约束 P1-3，P1-1、P1-2、P1-4 不依赖模型。
- P0 解释在真实种子客户数据上完成走查，且业务方确认「原因排序符合直觉」。
- 明确哪些数据允许出网；不允许出网时，P1-3 直接不做。
- P1-2 必须先冻结可注入变量清单；不能承诺资源/日历级假设。

## 7 不做的清单

| 诱惑 | 为什么危险 | 替代做法 |
|---|---|---|
| 模型自动重排、自动发布计划 | 发布动作影响生产，已发布版本不可覆盖；模型错误无人复核，回滚成本高 | 只给证据；重排与发布留在现有权限与确认流程 |
| 模型自动改订单交期、数量、优先级 | 直接改业务主数据，影响所有后续计划与交付承诺，误判无法追责 | 订单修改留在现有表单、校验与权限；AI 只读不写 |
| 模型自动修改约束权重或激活 DSL | 权重合计 100、激活有生命周期；错 5 分不会报错，只会让结果悄悄变差 | 只展示当前权重与扣分；修改走人工表单与校验 |
| 事件一到就自动增量重排 | 事件风暴会造成版本膨胀与计划抖动；没有事件源与阈值责任人 | 先登记事件、人工确认影响面，再走标准重排 |
| 全局聊天助手可调用任意接口 | 打开 prompt 注入面，可能越权、跨租户取数、误触发写操作 | 首版不做对话；后续只允许只读、白名单化参数 |
| 把全量订单/BOM/客户数据发给外部模型 | 数据合规风险高，且当前无相关约定 | 只发送聚合证据；不确定就不出网 |
| 模型直接生成交期承诺或插单建议 | 没有求解依据的日期是编造，会被当成对外承诺 | 日期只能来自当前任务状态或求解结果 |
| 根据用户点击自动学习调权重 | 无审计、无样本治理，结果不可解释 | 反馈只记录，不训练、不改权重 |
| 在甘特条上直接渲染模型结论 | 遮挡数据、结论易过期、用户无法核对 | 只渲染确定性标签；长内容进解释区 |
| 用模型补全主数据、BOM、日历 | 错误主数据会污染所有后续排产 | 主数据只走现有导入与校验 |
| 展示「置信度 85%」 | 伪精度，用户会把它当概率承诺 | 只用「依据完整/依据不足」 |
| 流式输出未经校验的模型文本 | 错误内容先入眼，事后撤回无效 | 校验通过后一次性展示 |
| 用 AI 替代现有 42200 等校验 | 会放松真实业务规则，错误更难定位 | 校验仍由现有规则负责，AI 不参与判定 |

## 9 环境变量配置（V05-01 实装口径）

> 说明：§1–§7 是 2026-11-05 之前的产品规划稿（当时 4 个 Agent 端点全是 501、不接模型）。V05-01/V05-02 已落地 `GET /agent/explain/{taskId}` 与可选的模型接线；**不配置任何模型变量时，行为与规划稿一致：不发起任何模型调用，`source=EVIDENCE`**。本节只约束「把模型打开」这一件事。

### 9.1 五个键

| 键 | 含义 | 缺省 | 是否必填 |
|---|---|---|---|
| `APS_AGENT_LLM_PROVIDER` | provider 选择：`deepseek` / `qwen` / `ollama` / `none` | `none` | 否；取 `none` 或留空即关闭 AI |
| `APS_AGENT_LLM_BASE_URL` | DeepSeek/Qwen 为 OpenAI 兼容 base（如 `https://api.deepseek.com/v1`）；Ollama 为原生 base | DeepSeek/Qwen 空；Ollama `http://127.0.0.1:11434`（yml 缺省） | DeepSeek/Qwen 必填；Ollama 可留空 |
| `APS_AGENT_LLM_API_KEY` | 密钥 | 空 | DeepSeek/Qwen 必填；Ollama 可留空 |
| `APS_AGENT_LLM_MODEL` | 模型名 | 有 yml 缺省：`deepseek-chat` / `qwen-plus` / `qwen3.5:9b` | 否；**留空走缺省**，要换模型才填 |
| `APS_AGENT_LLM_TIMEOUT_SECONDS` | 单次调用超时（秒） | `10`（等价 10000ms） | 否，可覆盖 |

### 9.2 优先级

**环境变量 > `application.yml` 同名配置项 > 缺省。** 三层都空时按 `none` 处理，不发起调用。

- 环境变量经 Spring relaxed binding 映射：`APS_AGENT_LLM_BASE_URL` ↔ `aps.agent.llm.base-url`，其余键同理。
- `application.yml` 里同时保留 `deepseek/qwen/ollama` 三个端点的旧字段（兼容 `DS_URL` 等旧变量）；**扁平字段非空时优先于对应端点字段**。
- 环境变量只影响**新启动的进程**；改完必须重启实例，运行中的实例不会热更新。

### 9.3 缺省行为（不配置）

- 服务正常启动，**绝不因为缺 key 启动失败**。
- `explain` 仍返回 `200`：`source=EVIDENCE`、`llm.configured=false`、`llm.provider=none`、`fallbackReason=NO_PROVIDER_CONFIGURED`，证据区照常可用。
- 不产生任何出网请求。

### 9.4 降级语义

响应对用户**始终是 HTTP 200**；模型失败只影响 `narrative` 与 `llm` 字段，证据区不变。

| 情形 | `llm.fallbackReason` | `source` | 说明 |
|---|---|---|---|
| provider 为空 / `none` / 名称未知 | `NO_PROVIDER_CONFIGURED` | `EVIDENCE` | `detail` 点名缺失项（如 `missing: APS_AGENT_LLM_BASE_URL, APS_AGENT_LLM_MODEL`） |
| 配置不全（缺 base-url / model / 非 ollama 缺 key） | `NO_PROVIDER_CONFIGURED` | `EVIDENCE` | 同上，逐项点名 |
| 上游非 200（如 401/403/429） | `PROVIDER_ERROR` | `EVIDENCE` | 只记状态码（如 `HTTP 401`）；**不回传上游错误正文** |
| 网络不可达 / 连接失败 | `PROVIDER_UNAVAILABLE` | `EVIDENCE` | 不暴露地址 |
| 超过 `APS_AGENT_LLM_TIMEOUT_SECONDS` | `TIMEOUT` | `EVIDENCE` | 客户端等待不超过配置超时的量级 |
| 输出不是合法 JSON 对象或为空 | `INVALID_OUTPUT` / `EMPTY_RESPONSE` | `EVIDENCE` | 结构化校验失败即整段丢弃，不部分保留 |

安全红线：

- **密钥不进入任何日志、响应体、异常信息**；不做掩码展示，直接不出现。
- `agent_run` 只落 `provider`、`degradation_reason` 与 `variables.{model,taskId,solveTaskId,latencyMillis,promptTokens,completionTokens}`，**不落 key**。
- 模型只做「证据改写」：prompt 只允许引用证据里的 `constraintId/constraintName/deduction/scoreImpact/taskId/solveTaskId/scoreHard/scoreSoft`，禁止编造约束、任务或数字；不产出处置建议。

### 9.5 现场演示

启动与自检统一用 [scripts/run-demo-llm.ps1](../../scripts/run-demo-llm.ps1)（独立端口，默认 18099，禁止 18085）；它启动后会自己调一次 `explain` 并打印 `source`。演示口径见 [demo-script.md](../guide/demo-script.md) 与 [demo-checklist.md](../guide/demo-checklist.md)。
