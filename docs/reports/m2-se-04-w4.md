## 一、软约束权重 E2E 的四个事实（回答 W2）

### 1. 两次求解的 score 原始字符串

| 场景 | Score 原文 |
| --- | --- |
| 基线（`MIN_TARDINESS=0`） | `0hard/-480soft` |
| 变更后（`MIN_TARDINESS=40`） | `0hard/-20580soft` |

来源：`SoftWeightsEndToEndTest` 真跑 Timefold，未 mock；断言 `hardScore=0`，`softScore` 分别为 `-480` 与 `-20580`（`Score` 文本即上表）。

### 2. 改了什么（8 条合计仍为 100）

| 规则 | 基线 | 变更后 | 变化 |
| --- | --- | --- | --- |
| MIN_TARDINESS | 0 | **40** | +40 |
| EDD | 16 | 6 | -10 |
| BALANCE_LOAD | 12 | 2 | -10 |
| PRIORITY_RESPECT | 24 | 14 | -10 |
| MIN_MAKESPAN | 16 | 6 | -10 |
| SPT | 8 | 8 | 0 |
| SAME_PRODUCT_CONTINUOUS | 12 | 12 | 0 |
| MIN_SETUP_TIME | 12 | 12 | 0 |
| **合计** | **100** | **100** | 0 |

### 3. 差值为什么能对上

- 该解中总逾期时长为 **510 分钟**：`510 × 40 = 20400` 分。
- 同时 MIN_MAKESPAN 权重从 16 降到 6，该解 makespan 为 **30 分钟**：`30 × (6 − 16) = −300` 分（即少扣 300）。
- 合计变化：`20400 − 300 = 20100`，与实测 `|−20580 − (−480)| = 20100` **完全一致**。
- 结论：权重不是“写进配置没人读”，而是逐分进入了 `softScore`。

### 4. 测试里的断言（不是“不抛异常”）

`SoftWeightsEndToEndTest` 中：

- `assertThat(solution.getScore().getHardScore()).isEqualTo(0)`
- 基线断言 `softScore == -480`
- 变更后断言 `softScore == -20580`
- 且断言 `|softScore₂| > |softScore₁|`（方向符合“逾期权重提高 → 逾期惩罚更重”）
- 同一道题、同一份数据，仅 `SolveConfig.parameters.softWeights` 不同


- 新 O-2 的 OP10 与 O-3 的 OP10 **同一时刻 06:10 开工**，直接冲突。
- 说明：无 `startingSolution`、也未把未受影响任务作为“已占用时段/固定指派”喂给求解器，求解器题面里只有 O-2，于是把它排到了最早可用点。
- 未受影响任务确实“逐字段不动”，但这是**因为没有让它们参与求解**，而不是因为求解器尊重了它们；本实现应表述为“**带订单排除的局部重排**”，既不是 warm start，也不是能保持全局可行的增量。

1. 把未受影响任务以固定起始时间 + 固定资源（pinned）的形式放进题面，作为占用约束；
2. 或接受“局部重排”语义，但由调度侧保证重排窗口内无其他订单占用（按时间窗切题）。

## 七、关于“整单排除”的降级与判定位置（回答第 3 点）

### 1. 硬约束就位后能否降级为“只排除锁定任务本身”？

**`TIME_WINDOW` / `RESOURCE` 可以；`FROZEN`（含订单级 `freeze_status`）不建议，需要 W1 先把“冻结粒度”定死。**

- `TIME_WINDOW` / `RESOURCE` 的语义是“约束某个任务的时间/资源”，同订单其他任务本就不在锁范围内。求解期有硬约束后，只要把锁定任务 pin 住（固定开始时间 + 固定资源），随后把整单放进题面即可：锁定任务被硬约束钉住，其余任务围绕它重排。此时“整单排除”可以降级为“只排除/钉住锁定任务本身”。
- `FROZEN` 目前被当作**订单级冻结**（`orders.freeze_status`）与**任务级冻结**（`task.status='FROZEN'`）两层，且验收口径是“取交集、任务级不得更宽”。在 W1 没明确“FROZEN 只冻结该任务还是整单”之前，不能把 FROZEN 降级为单任务排除，否则可能放宽订单级冻结。
- 前提条件：降级后必须同时满足 ① 锁定任务真的 pinned（不能被“移动/交换”类 move 改到别处）；② 未受影响/未锁定任务也以 pinned 或占用时段的方式进入题面，否则会重演 4.4 的重叠问题。

### 2. 当前判定是“任一任务”还是“全部任务”？

**改造前是“任一任务”就把整单排除**（订单级粒度）；按 C21 第 6 条改造后，整单排除仅在订单级
`freeze_status` 保留，任务级 `FROZEN` 只钉住该任务。改造后的判定如下。

**订单级**：只认 `orders.freeze_status`，不再看任务锁。见
[IncrementalSolveRepository.java](file:///d:/tools/smart-aps-agent/aps-infrastructure/src/main/java/com/hengce/aps/infrastructure/persistence/schedule/IncrementalSolveRepository.java#L77-L85)：

```sql
SELECT DISTINCT o.id
  FROM orders o
 WHERE o.tenant_id = ? AND o.sandbox_id = ? AND o.deleted = false
   AND o.freeze_status <> 'UNFROZEN'
```

**任务级**：只有 `lockType=FROZEN` 或 `status=FROZEN` 才跳过该任务本身，`TIME_WINDOW/RESOURCE`
不再跳过（它们要参与重排，由 W2 的硬约束限制可行域）。见
[IncrementalSolveService.java](file:///d:/tools/smart-aps-agent/aps-service/src/main/java/com/hengce/aps/service/schedule/IncrementalSolveService.java#L127-L145)：

```java
Set<UUID> frozenOrderIds = new HashSet<>(incrementalRepository.findFrozenOrderIds(tenantId, sandboxId));
...
if (frozenOrderIds.contains(task.orderId())) { skippedLockedTasks++; continue; }   // 订单级
if ("FROZEN".equals(task.lockType()) || "FROZEN".equals(task.status())) {          // 任务级
    skippedLockedTasks++;
    continue;
}
```

**未受影响任务作为 pinned 进同一份题面**：`pinnedOrderNos` = 场景内不属于受影响订单的订单号，
经 `parameters` 传入装配器常量 `ScheduleProblemAssembler.PARAM_PINNED_ORDER_NOS`
（[ScheduleProblemAssembler.java](file:///d:/tools/smart-aps-agent/aps-service/src/main/java/com/hengce/aps/service/schedule/ScheduleProblemAssembler.java#L160)
与 [IncrementalSolveService.java](file:///d:/tools/smart-aps-agent/aps-service/src/main/java/com/hengce/aps/service/schedule/IncrementalSolveService.java#L162-L172)）。
装配器把它们的 task 行读进同一份 `ScheduleProblem` 的 `frozenAssignments`（`forcePinned=true`），
`TimefoldModelBuilder` 对 `existing.frozen() && 有 start/resource` 的任务置 `@PlanningPin`
（[TimefoldModelBuilder.java](file:///d:/tools/smart-aps-agent/aps-solver/solver-timefold/src/main/java/com/hengce/aps/solver/timefold/TimefoldModelBuilder.java#L218-L247)），
因此 pinned 任务会占用资源区间、参与 `resourceNoOverlap` 与 `operationDependency`，
受影响任务只能落在它们留出的缝隙里。

结论：锁定粒度已从「整单」改为「任务级 FROZEN 只钉该任务 + 订单级 freeze_status 整单约束」，
同订单其余任务照常重排；未受影响订单任务以 pinned 形式进入同一份 problem。

## 九、增量可执行性改造（A 方案）与锁语义修复

### 9.1 锁字段映射位置（缺口 1）

装配层不再把任何锁压成 `FROZEN`，按真实 `lock_type` 分别映射
（[ScheduleProblemAssembler.java](file:///d:/tools/smart-aps-agent/aps-service/src/main/java/com/hengce/aps/service/schedule/ScheduleProblemAssembler.java#L633-L648)）：

```java

        || "FROZEN".equals(row.status()) || "FROZEN".equals(row.lockType());
new TaskAssignment(..., row.status(), frozenLevel, row.version(),
        row.lockType(), row.lockedFrom(), row.lockedTo(), row.lockedResourceIds());
```

求解模型层按同一口径回填三项锁属性
（[TimefoldModelBuilder.java](file:///d:/tools/smart-aps-agent/aps-solver/solver-timefold/src/main/java/com/hengce/aps/solver/timefold/TimefoldModelBuilder.java#L243-L247)）：

```java
if (existing != null) {
    task.setLockType(existing.lockType());
    task.setLockedFrom(toLocal(existing.lockedFrom()));
    task.setLockedTo(toLocal(existing.lockedTo()));
    task.setLockedResourceIds(existing.lockedResourceIds());
}
```

口径与 W2 一致：`TIME_WINDOW` 闭区间（`start >= lockedFrom && end <= lockedTo`）、
`RESOURCE` 主资源 ∈ `lockedResourceIds`（空集合视为未锁定）、`NONE/null` 不约束、
`FROZEN` 优先（命中后不再叠加窗/资源约束）。

### 9.2 增量粒度（缺口 2）

- 订单级：仅 `orders.freeze_status <> 'UNFROZEN'` 整单排除；
- 任务级：仅 `lock_type='FROZEN'` / `status='FROZEN'` 跳过该任务本身；
- 未受影响任务以 pinned 进入同一份 problem（`PARAM_PINNED_ORDER_NOS`）；
- 落库只写受影响订单；pinned 任务不重写，因此逐字段天然不变。

### 9.3 pinned 与三层锁的优先级（C21：`FROZEN > lockType > frozen:boolean`）

- `lockType=FROZEN`（或 `status=FROZEN`）→ `TimefoldModelBuilder.isFrozenLevel` 命中，
  固定原资源与开始时间，且 `effectiveLockType=FROZEN` 走 `frozenStartTime/frozenResource`；
- `lockType=TIME_WINDOW/RESOURCE` → 锁字段照常回填，任务**可移动**，由 W2 的硬约束限制可行域；
- `frozen:boolean`（增量 pinned 标记）→ `@PlanningPin`，固定在原资源/开始时间。
- 两者叠加时：pinned 只是“不允许移动”，`lockType` 约束仍会照常求值；若 pinned 的原位
  违反 `TIME_WINDOW/RESOURCE`，会暴露为硬违规（数据不一致），不会被 pinned 静默吞掉。
  **没有用 pinned 覆盖 lockType 语义，优先级仍是 FROZEN > lockType > frozen:boolean。**

### 10.4 守卫范围、全量验收与报错语义

**守卫范围 = 新写任务 × 全表。** `findResourceOverlaps(tenant, sandbox, insertedTaskIds)`
的 SQL 是 `task t1 JOIN task t2`（同 `resource_id`、半开区间 `[start,end)` 相交、`t1.id<t2.id`），
`insertedTaskIds` 非空时只追加 `AND (t1.id IN (…) OR t2.id IN (…))` —— 即“至少一侧是
本轮新写任务”，另一侧可以是任意历史行。不传 `taskIds` 即纯 `tenant+sandbox` 全表。

**全量验收（不传 taskIds）原始输出（本轮最后一次求解 solve 29 之后）：**

```text
 task_rows | overlap_pairs
-----------+-------------
         6 |             0
```

明细查询（同一 SQL 去掉 count）返回 0 行。对照参考：solve 14 触发守卫时，
误差为 5 对，明细前几对为 `20/32@…c1 [2026-11-03T23:00Z,2026-11-04T09:10Z) vs
[2026-11-03T23:00Z,2026-11-04T19:10Z)` 等。

**守卫触发时调用方看到什么（实测 solve 14，`GET /api/v1/solve-tasks/14`）：**

```json
{"code":0,"message":"success","data":{"taskId":14,"status":"FAILED","progress":1.0,
 "degraded":true,"errorCode":"ENGINE_ERROR","engineFallback":true,
 "engineFallbackReason":"ENGINE_ERROR","fallbackMode":"HARD_ONLY",
```

即 HTTP 200 + `status=FAILED` + `ENGINE_ERROR` 降级标记，**不是 500、不是未捕获异常**，
`errorMessage` 带原因（含重叠对明细）。

**事务语义。** `ScheduleResultWriter.persist` 是
`@Transactional(rollbackFor = Exception.class)`（[ScheduleResultWriter.java](file:///d:/tools/smart-aps-agent/aps-service/src/main/java/com/hengce/aps/service/schedule/ScheduleResultWriter.java#L65)），

`task` 表保持求解前状态（solve 14 前后 6 行 id/时间/`created_at` 未变）。
`solve_task` 由生命周期服务在事务外的失败分支写成 `FAILED`，
所以不存在“`SOLVED` 但任务没落库”的半截状态。

### 10.9 软约束权重的并发隔离取证（只取证，未改实现）

**结论：并发是安全的，但安全来自“串行化”而不是“并行隔离”——同一进程内同一时刻只有一个
求解会话处在 `activate → disable` 区间；第二个请求要么排队等锁，要么拿到明确的 `FAILED`，
不会静默用着别人的权重返回 `SOLVED`。代价是求解吞吐恒为 1，且等待上限恰好等于自身超时。**
